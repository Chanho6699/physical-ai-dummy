# Pick & Drop dataset build: V2-clean + V3 start-coverage -> combined65

Generated by `scripts/build_pick_drop_datasets.py` (LeRobot v0.6.2, `lerobot.datasets.dataset_tools`:
`modify_tasks`, `merge_datasets` -> `lerobot.datasets.aggregate.aggregate_datasets` - the same
functions the official `lerobot-edit-dataset` CLI wraps). No manual parquet task editing, no folder
`mv`, no training, no checkpoints, no git operations. Original datasets were never opened in write
mode; every check below re-confirms that.

## LeRobot API used (researched before writing this script)

- `repo_id` is **not** stored in any LeRobot v3.0 metadata file (`meta/info.json` has no such
  field, confirmed by reading it directly) - it is a client-side string passed to
  `LeRobotDataset()`. A bare `mv` would not corrupt anything LeRobot reads, but it also wouldn't
  give any of the guarantees below - the actual risk avoided here is (a) hand-editing task
  columns and missing one of the four places LeRobot denormalizes a task string, and (b) hand-
  rolling episode/index/chunk-file bookkeeping for a merge.
- `lerobot.datasets.modify_tasks(dataset, new_task=...)` - **in-place** official task editor.
  Touches exactly: `meta/tasks.parquet`, `task_index` column in every `data/**/*.parquet`, `tasks`
  column in every `meta/episodes/**/*.parquet`, and `total_tasks` in `meta/info.json`. Because it
  is in-place, this script points it only at **copies** of the source datasets, never the
  originals.
- `lerobot.datasets.merge_datasets(...)` -> `aggregate_datasets(...)` - official merge path.
  Internally calls `validate_all_metadata()` which asserts equal `fps`, `robot_type`, and
  `features` (via `features_equal_for_merge`, ignoring only video-encoder-parameter differences)
  before touching any files, and rebuilds `episode_index`, `dataset_from_index`/
  `dataset_to_index`, and chunk/file bookkeeping from scratch.

## 6. Coverage sanity check vs. `reports/grid35_v2_vs_start_coverage_v3/`

The static/low-motion coverage, start-pose-diversity, and immediate-WOULD_CLAMP metrics were
recomputed **directly from the on-disk `combined65` dataset**, reusing the exact functions from
`scripts/analyze_v2_vs_v3_start_coverage.py` (same 1deg/3-frame movement detector, same
`configs/safety_gate.yaml` thresholds), and compared against that report's `combined_v2_plus_v3`
numbers (which were computed by literal in-memory concatenation of the two source datasets, before
any dataset file existed on disk):

| metric | on-disk combined65 | prior report (in-memory concat) | match |
|---|---:|---:|---|
| static/low-motion frame fraction | 10.3296% | 10.3296% | **exact match** |
| start-pose pairwise L2 median | 12.7113 deg | 12.7113 deg | **exact match** |
| shoulder_lift immediate %>WOULD_CLAMP | 0.0000% | 0.0000% | **exact match** |
| elbow_flex immediate %>WOULD_CLAMP | 0.0454% | 0.0454% | **exact match** |

All four numbers match to full floating-point precision (compared at 1e-6-1e-9 tolerance) - no
discrepancy to investigate. This confirms the on-disk merge (task-string change + `aggregate_datasets`
repacking of data/video files) did not alter any `observation.state`/`action` value: the
combined65 dataset behaves numerically identically to a literal concatenation of the two original
datasets, just with the corrected task string and proper LeRobot v3 bookkeeping.

## What did NOT change

- `action`, `observation.state`, `timestamp`, `frame_index` values - byte-identical to the
  originals in both source-derived datasets (verified in section 2), and therefore also identical
  within the merge (verified in section 6).
- Camera videos (`observation.images.workspace`, `observation.images.wrist`) - byte-identical
  copies in the two Pick&Drop datasets (section 2); repacked into single per-camera mp4 files in
  the merge (still validated frame-count/reference-consistent, section 5), no re-encoding of pixel
  content beyond the video-file concatenation itself.
- `meta/stats.json` per-feature statistics - carried through unchanged in the two Pick&Drop
  datasets; re-aggregated (not recomputed from raw frames) for the merge, per
  `aggregate_datasets`'s own `finalize_aggregation`.
- The two **original** dataset directories - untouched throughout, proven by SHA-256 checksums
  before/after every stage (section 2).

## What DID change

- The single task string, in all four places LeRobot denormalizes it, in the two new Pick&Drop
  datasets and their merge.
- `episode_index`, `index` (global row index), and `task_index` values - renumbered as required by
  the merge (0..64 episodes, 0..21326 global rows), exactly as `aggregate_datasets` is designed to
  do; not a content change to any observation or action.

## Answers

**1. 실제 생성된 dataset path 3개**

- `data/so101_cube_pick_drop_start_coverage_v3_clean`
- `data/so101_cube_pick_drop_combined65_v1`

**2. 각 episode/frame/task count**
- V2 Pick&Drop: 35 episodes / 11,505 frames / task count 1
- V3 Pick&Drop: 30 episodes / 9,822 frames / task count 1
- Combined65: 65 episodes / 21,327 frames / task count 1

**3. combined65 검증 결과**
episode_index 0..64 연속, dataset_from/to_index boundary 정상, frame count(21,327)=V2+V3 정확히
일치, FPS 30, state/action 6D, workspace+wrist camera 존재, NaN/Inf 없음, 모든 data/video 참조가
실제 파일과 일치 - 전 항목 통과 (`all_ok: true`). Coverage sanity check(정적 비율/시작 다양성/
WOULD_CLAMP)도 기존 in-memory 결합 계산값과 완전히 일치.

**4. task semantics가 정확히 Pick & Drop으로 바뀌었는지**
예. 두 신규 dataset과 combined65 모두 task string이 정확히
`"Pick up the cube and drop it into the bin."` 하나뿐이며, 65개 episode 전부 이 문자열과
일치함을 확인했다. 원본의 `"Pick up the cube and place it in the target area."`는 새 dataset
어디에도 남아있지 않다.

**5. 원본이 그대로 보존되었는지**
예. `data/so101_cube_xy_grid35_v2_clean`, `data/so101_cube_xy_start_coverage_v3` 두 원본 모두
작업 시작 전/복사+retask 직후/merge 직후 세 시점에서 파일 단위 SHA-256 체크섬이 완전히 동일함을
확인했다 (112개 파일씩, 추가/삭제/변경 0건). 새 Pick&Drop dataset들의 action/state/timestamp/
frame_index/video/stats도 원본과 (task 컬럼을 제외하고) 셀 단위로 동일함을 확인했다.

**6. fresh training에 투입 가능한 상태인지**
데이터 무결성 관점에서는 그렇다 - 65-episode combined dataset은 모든 integrity/schema/coverage
검증을 통과했고, 기존 V2-vs-V3 분석에서 확인된 안전한 immediate action/개선된 start diversity가
merge 후에도 수치상 그대로 유지됨을 재확인했다. 다만 이 작업 자체는 "아직 training 하지 말 것"
지시에 따라 학습을 수행하지 않았으며, training 실행은 별도 승인 이후 단계다.
